<Update label="September 13, 2026" description="Infrastructure - DNS resolution during the V3 to V4 migration">
  ## V3 to V4 migration - if a Despia page says "This site can't be reached"

  All Despia addresses are resolving normally again. On September 13, while internal infrastructure moved as part of the V3 to V4 migration, a few despia.com addresses such as v3.despia.com stopped resolving for a short time.

  This was a hosting-level address lookup issue. Your projects, builds and account data were never touched and remain fully secured.

  We are migrating Despia V3 to Despia V4, moving onto self hosted infrastructure and rebuilding Despia in Despia itself, so that we run on exactly what you run on.

  **If your browser still shows the error:**

  If you still see "This site can't be reached" or the code `DNS_PROBE_FINISHED_NXDOMAIN`, your device or network cached the failed lookup. It clears on its own within about 30 minutes. Any one of these clears it immediately:

  - **Restart your Wi-Fi router.** This fixes every device on the network at once.
  - **Switch networks briefly.** Your phone's hotspot works.
  - **Set your device DNS to 1.1.1.1.** On Mac: System Settings, Network, your connection, Details, DNS, add 1.1.1.1. On Windows: Settings, Network and internet, your connection, DNS server assignment, Edit, Manual, IPv4 on, Preferred DNS 1.1.1.1. On iPhone: Settings, Wi-Fi, the i next to your network, Configure DNS, Manual, add 1.1.1.1. On Android: Settings, Network and internet, Private DNS, enter one.one.one.one.

  Then reload the page. In Chrome, if it still fails, open `chrome://net-internals/#dns` and click Clear host cache.

  No dashboard configuration changes, rebuild steps, or integration code changes are required. The only action needed is clearing a stale DNS cache on your own device, and only if you are still seeing the error.
</Update>

<Update label="September 03, 2026" description="Age Assurance - OS age range checks on iOS and Android">
  ## Age Assurance

  Despia apps can now read the age range the operating system already holds for a user, on iOS and Android, from a single call that returns the same shape on both platforms. Apple Declared Age Range and Google Play Age Signals sit behind one bridge, so a build can gate mature content, unlock adult-only features, or soften an experience for a minor without ever asking for a birthdate.

  **What ships today:**

  - **`ageassurance://check`.** Fires the platform consent sheet and delivers a verdict to `window.onAgeAssuranceResult`. Pass `gates` as up to three comma-separated ages you actually gate on, and `id` to correlate the response. Nothing throws and nothing rejects: every outcome, including every failure, arrives as a verdict with a `status` of `shared`, `declined`, `verification_required`, `not_applicable`, `unavailable`, or `error`.
  - **Three-state gates.** Each key in the `gates` map answers `true`, `false`, or `null`, where `null` means the requested age falls inside the returned band and the operating system genuinely did not answer. Test for `=== true` before unlocking anything. Reading `null` as `true` is what hands adult content to a minor and costs an app its listing.
  - **Assurance tiers.** Every shared verdict carries how the age was established: `self_declared`, `guardian_declared`, `verified_estimated`, `verified_strong`, or `unknown`. Require a stronger tier for the flows that need one.
  - **`ageassurance://resolve`.** Android only. Sends a user into Play's own verification flow when Google answers `verification_required`. On iOS the command is absent from `ageAssuranceFeatures` and answers `error` with `unsupported_action`.
  - **`ageassurance://last` and `ageassurance://forget`.** `last` replays the retained verdict without prompting. `forget` drops it on the native side and resets `ageAssuranceVerdict` to `null`, which is what you call on logout or an account switch so the next person to sign in cannot read the previous user's age range.
  - **Capability globals.** `ageAssuranceAvailable`, `ageAssuranceProvider`, `ageAssuranceReason`, `ageAssuranceFeatures`, and `ageAssuranceVerdict` are plain globals that never prompt. Branch on these rather than on the operating system version or the user agent. They exist only in the top-level page: an `<iframe>` never receives them and an `ageassurance://` call from one is refused.

  Coverage differs sharply by platform. Android reaches effectively every device from 6.0 upward, while iOS requires 26.2 or later and answers `unavailable` on the Simulator, so real iOS testing needs a physical device. Because Apple shapes its band from the ages passed at call time and Google returns bands configured in Play Console, the same user can produce different `ageLower` and `ageUpper` values on each platform. The `gates` map is the part that means the same thing everywhere.

  Everything the web app receives is client-side and can be forged. Treat the verdict as a signal that shapes the experience, and for anything load-bearing echo it to your backend paired with App Attest or Play Integrity.

  **Packages:**

  - [despia-native](https://www.npmjs.com/package/despia-native)

  This feature requires action. The native SDKs are linked at build time, so enabling the Age Assurance addon under App, then Addons is not enough on its own. Enable Declared Age Range on your identifier in the Apple Developer portal and regenerate the provisioning profile that build uses, accept the Age signals terms in Play Console and set your bands there, then rebuild with an increased version code. Until all of that is done every call answers `status: "unavailable"` with `reason: "not_configured"`, silently and with no warning. Confirm `despia.ageAssuranceAvailable` is `true` on the new install before relying on any verdict.
</Update>

<Update label="August 08, 2026" description="Easy OAuth - HTTPS sign-in callback on your own domain">
  ## Easy OAuth

  Social sign-in can now finish on your own domain instead of on a custom scheme, with the provider's redirect landing directly in your app and no intermediate callback page to build.

  Pass `type=https` on the `oauth://` scheme and the runtime watches your entire host for the provider's redirect. When it lands, the secure browser session closes and your app loads that exact callback URL, query string and fragment intact.

  **What ships today:**

  - **The `type=https` parameter.** One flag on the `oauth://` scheme selects the flow. There is no callback path to configure, because the session watches the whole host and any redirect home finishes the login.
  - **Verbatim delivery.** The callback URL loads exactly as the provider sent it, so implicit flow providers that return tokens in the fragment now work. The legacy flow rebuilds from path and query only, which drops the fragment.
  - **Cookies land in your app.** The redirect is recognised at navigation time and never fetched inside the browser session, so your app makes the only real request and any `Set-Cookie` header on it is written to your app's own store.
  - **Capability detection.** `despia.httpsAuthCallback` reports whether the current device can finish on your domain, so your page can pick the right `redirect_uri` before it builds the authorize URL. That choice cannot be changed once the flow starts.
  - **Association failure reporting.** `window.onAuthCallbackError(host, code)` fires when the domain association is broken, a case iOS otherwise reports with the same code it uses for an ordinary user cancellation.
  - **iOS and Android parity.** iOS runs the session on `ASWebAuthenticationSession` (17.4 and later). Android runs an Auth Tab where the browser supports it, falling back to a verified App Link with a Custom Tab.

  Setup is required before the flow can work. Your domain needs an `apple-app-site-association` file carrying a `webcredentials` section and an `assetlinks.json` file carrying your Play app signing key fingerprint, Associated Domains has to be enabled on your main Bundle ID, and Web App Synchronization has to be turned on under Addons. The capability is written into the binary at build time, so it reaches users only through a store deployment on a raised version. The [Easy OAuth documentation](/native-features/oauth/easy-login-flow) covers each step, including where to find the SHA-256 fingerprint in Play Console.

  This is opt-in and additive. Existing integrations are unaffected: a `despia()` call that does not pass `type=https` runs the legacy custom scheme flow unchanged, needs no code edits, and keeps working on devices that cannot support the new flow.
</Update>

<Update label="August 08, 2026" description="Android - 16 KB page size compliance and build verification">
  ## Android 16 KB page size compatibility

  Android builds now ship native libraries that meet Google Play's 16 KB page size requirement, and every build is checked against that requirement before the bundle is uploaded.

  Previously the Android runtime included a build of `libsqliteJni.so` produced before NDK r28. Its segments were aligned correctly, so the usual alignment check passed, but its RELRO region stopped partway through the writable segment. The loader cannot apply protection to a partial page, so it dropped that protection entirely, and Google Play flagged the bundle for arm64-v8a and x86_64.

  **What changes:**

  - **Updated SQLite native library.** The runtime now resolves androidx.sqlite to a version built with NDK r28, which pads the RELRO region out to a 16 KB boundary. This is the library named in the Play Console warning.
  - **Release gate on every build.** Each Android build is inspected after compilation and before upload. Any 64-bit native library that is not 16 KB compatible fails the build with the offending file named, so a future dependency update cannot reintroduce the problem silently.
  - **Native libraries stay uncompressed.** Libraries are kept uncompressed and page aligned inside the package, so the system maps them directly instead of extracting copies at install time and discarding their alignment.

  No dashboard configuration or integration code changes are required. Rebuild your Android app to pick up the updated runtime.
</Update>

<Update label="June 11, 2026" description="In-app rating - native star prompt without leaving the app">
  ## Native in-app rating prompt

  The `rateapp://` scheme now presents the operating system's native star rating prompt as a sheet inside your app, so users can leave a rating in a single tap without the session being interrupted.

  Previously the scheme could route users out to the store listing depending on the `showcustomrateappdialog` configuration flag. A rating request cost the user their place in the app and required a manual trip back, which is the main reason in-app rating prompts convert poorly.

  **What changes:**

  - **Native prompt on the bare scheme.** Both `rateapp://` and `rateapp://rating` present the native rating sheet in place and never navigate away from your app.
  - **Explicit opt-in for the review composer.** `rateapp://review` is now the only variant that leaves the app. It opens the store's write-review composer for your listing, which makes it suited to an explicit "Write a review" button rather than an automatic prompt.
  - **`showcustomrateappdialog` is deprecated.** The flag is no longer read. The bare scheme always shows the native prompt regardless of what it is set to.

  The operating system rate limits the native prompt to a small number of displays per user per year and suppresses it silently once that budget is spent. Treat the command as a request rather than a guarantee, and do not block a flow or show a confirmation on the assumption that the user saw it.

  Existing `rateapp://` calls need no changes and pick up the native prompt automatically. If your app relied on `showcustomrateappdialog` to send users to the store listing, switch those calls to `rateapp://review` to keep the previous behaviour.
</Update>

  Android apps that disable the advertising ID can now use OneSignal. Previously, turning off tracking excluded the OneSignal SDK from the build entirely.

  The OneSignal SDK declares `com.google.android.gms.permission.AD_ID` by default, which contradicts a Play Console data safety declaration stating the app does not collect an advertising identifier.   Existing apps need a fresh native build to pick this up. No dashboard configuration or integration code changes are required beyond leaving the tracking setting off.

<Update label="July 31, 2026" description="File Picker - native pickers driven by the accept attribute">
  ## File Picker

  File inputs now open the native picker that matches what the upload actually accepts, driven entirely by the standard `accept` attribute. Existing upload forms get native pickers with no code change.

  **What ships today:**

  - **Accept-driven routing.** The `accept` value is parsed when the user taps the input, mapped to native file types, and the matching picker is presented scoped to those types. Extensions, MIME types, and wildcards are all understood, and the mapping is generic rather than a fixed list, so `.mp3` and `.dwg` resolve the same way.
  - **Photo picker for media.** `image/*`, `video/*`, `image/*,video/*`, and concrete types such as `image/png` open the system photo picker filtered to that type, keeping users out of the file system entirely.
  - **Documents picker for everything else.** Audio, PDFs, archives, and mixed media open the documents picker scoped to the accepted formats. An unrecognised extension is dropped from the scope rather than blocking the picker.
  - **Direct camera capture.** Pairing `capture` with a media `accept` skips the picker and opens the camera. `environment` selects the rear lens, `user` the front. On non-media inputs `capture` is ignored and normal routing applies.
  - **Multi-select.** The standard `multiple` attribute enables multi-select in whichever picker opens, including the documents picker. Cancelling leaves the `FileList` empty and raises no error, so a cancel stays distinguishable from a genuine failure.
  - **Browser picker handoff.** The `filepicker://type?native_overwrite=true` command returns every file input on the page to the default web picker. The setting survives navigation and resets on relaunch, so pages that depend on it should set it on load.
  - **Configurable upload sources.** The sources offered when an input has no `accept` value are set per app in the Despia Editor: camera and gallery, camera only, or gallery only.

  Selected files arrive as ordinary `File` objects backed by a URL, so a long recording or a large video is streamed on upload rather than copied through memory first.

  Full documentation is available on the [File Picker](/native-features/file-picker) page.

  No integration code changes are required for accept-driven routing. Changing the upload source mode in the Despia Editor requires a fresh native build.

  **Packages:**

  - [despia-native](https://www.npmjs.com/package/despia-native)
</Update>

<Update label="July 31, 2026" description="Dynamic App Source - custom URL scheme">
  ## Custom URL scheme

  The scheme your app registers with iOS and Android is now editable in **Despia > App > Settings > Dynamic App Source > URL Scheme**.

  Until now the value was generated from your app name on the first build. App names containing spaces, punctuation, accented characters, or a leading digit produced a scheme the operating system will not register, and App Store Connect flags the malformed entry at submission rather than at build time.

  **What ships today:**

  - **Editable field.** Enter the value on its own, with no `://` suffix and no path. Entering `myapp` registers `myapp://`.
  - **Independent of app name.** Renaming your app no longer changes the scheme, so a live login flow survives a rename.
  - **Compliance control.** Apps whose generated scheme was rejected can now set a valid one without renaming the app itself.

  The scheme is what closes a native authentication session and hands tokens back to your WebView, so changing it on a live app means registering the new value alongside the old one in every OAuth provider dashboard before shipping. Existing apps keep their current scheme until the field is edited. See [URL Scheme](/native-features/url-scheme) for the compliance rules and the migration checklist.

  Editing the field is a native configuration change and requires a fresh build. Until that build is installed, the binary on the device answers to the old scheme only, and return links fire silently with no error.
</Update>

<Update label="July 29, 2026" description="Local AI - cutting ties with Cactus, building our own engine">
  ## Cutting ties with Cactus, investing in our own local AI

  Despia demo apps no longer ship with the Cactus inference backend, and Cactus is being removed as the engine behind the local AI feature entirely.

  Cactus was open source when we adopted it. That changed. The current license is source-available, with commercial use gated behind funding and revenue thresholds. Despia does not ship one app, it ships an engine inside every customer's app, so a dependency like that becomes a liability for every project built on the platform.

  We are not willing to build Despia apps on infrastructure that is not open source, or that we do not control enough to guarantee quality and fair pricing. So we are building the engine ourselves.

  **What we are investing in:**

  - **A fully open source local AI ecosystem.** Apache-2.0, no usage limits, no revenue thresholds, no license checks, no telemetry. Built on llama.cpp and whisper.cpp, both MIT.
  - **Usable outside Despia.** The engine ships as standalone Swift, Kotlin, and TypeScript packages, so React Native and Capacitor apps can use it directly without touching Despia at all.
  - **First-class support inside Despia.** In Despia it stays fully low-code - the `intelligence` capability keeps its existing action names, arguments, and return shapes, so integration code written today does not change when the new engine lands.
  - **Streaming, tool calling, and MCP.** Token streaming, a native tool-calling loop wired to your app's own module actions, and an MCP client, across iOS, Android, macOS, and Windows.

  No dashboard configuration changes, rebuild steps, or integration code changes are required today. Apps relying on on-device inference should treat the capability as unavailable until the new engine is released.
</Update>

<Update label="July 28, 2026" description="Offline support - PWA service workers on iOS and Android">
  ## PWA service workers

  Despia apps can now run the service worker your web app already ships, giving you a working offline mode driven entirely by standard web APIs with no build tools and no native offline layer.

  **What ships today:**

  - **Service worker registration.** Registration, installation, activation, and fetch handling behave the same inside the app as they do in a browser PWA, on both iOS and Android.
  - **Cache storage.** Precached documents, assets, and API responses are served when the device has no connection, using whatever caching strategy your worker defines.
  - **Offline state through web APIs.** IndexedDB and localStorage are available for persisting sessions, drafts, and queued writes, so login screens and app state survive an offline launch.

  Enable it under App > Settings > Offline Support > PWA, then increase the version code and rebuild. Offline support is a native runtime setting, so builds produced before the toggle was flipped ignore service worker registration entirely.

  Your service worker is the single point of failure. A worker that caches once and never refreshes will pin users to an old release, block over the air updates, and can open the app to a white page when a cached document references assets that no longer exist. Serve from the network first while online, write successful responses back into the cache, and change the cache name on every release so stale entries are cleared on activate. See [PWA service workers](/native-features/service-workers) for the reference implementation and the offline verification test.

  A dashboard change and a fresh native build are required. No integration code changes are needed beyond the service worker in your own web app.
</Update>

<Update label="July 26, 2026" description="Usage Descriptions - editable iOS and Android permissions">
  ## Usage Descriptions

  Every permission your app declares is now an editable field under App > Settings > Usage Descriptions. You control the wording of each iOS purpose string, and clearing a field removes the permission from the build entirely.

  Until today, every Despia binary shipped a broad default permission set so that any web API you reached for would work without a new native build. Apple now runs an automated analysis of purpose strings at submission and rejects binaries under Guideline 5.1.1 when a string is generic or when a permission is declared for a resource the app never uses.

  **What ships today:**

  - **Editable purpose strings.** Each of the seventeen supported permissions has its own field. Write your own copy describing what your app does with the data, or use Revert to Default to restore the Despia wording and edit from there.
  - **Removal by clearing the field.** An empty field removes the key from `Info.plist`. It also strips the feature, its native code, and any dependencies or libraries it imported, so exported Xcode and Android Studio projects contain no dead capability.
  - **Android manifest mapping.** The iOS keys are mapped to their Android equivalents. Filling in a usage description adds the matching feature and permission to the Android manifest, and clearing it removes them from both platforms. The Health keys and Tracking are iOS only.
  - **Supported keys.** Camera, Microphone, Photo Library, Save to Photos, Location While Using, Background Location, Always-On Location, Bluetooth, Contacts, Calendar, Face ID, Health Read, Health Write, Speech Recognition, NFC Scanning, and Tracking. Push Notifications is also a field, holding the copy for your own priming screen, since iOS does not allow custom text in the system notification alert.

  A field must be completely empty for the permission to be removed. A single space counts as a value and the key stays in the build.

  Removing a permission removes it from the binary, and no over-the-air update can add it back. If web code later calls an API whose usage description was removed, iOS terminates the app. Gate native capabilities on the app version using the `getappversion://` scheme, ship the binary carrying the new usage description first, then push the web update that enables the feature.

  Existing apps keep their current permission set until you edit it. Changes to usage descriptions apply on the next native build.
</Update>

<Update label="July 26, 2026" description="V4 - core runtime being open sourced under MIT">
  ## Open sourcing the Despia V4 runtime

  Ahead of the V4 release, the core runtime is being prepared for publication as open source under the MIT license. The editor follows later this year.

  The V4 runtime is a dynamic kernel. Every capability above it - WebView, native UI, web UI, backend - is a package that the kernel loads at runtime. What gets open sourced is the kernel, the brain of the system. The packages stay in a closed source folder and are not part of the release.

  **What is included:**

  - **The kernel.** Package loading, command dispatch, and lifecycle management - the layer everything else runs on.
  - **The component contract.** The components folder and the attribute model that text, image, button, and every other primitive are declared against. Anyone can implement against it.
  - **Nothing above the kernel.** The Despia WebView package, native UI package, web UI package, and backend package are excluded and remain closed source.

  **Why:**

  - **Auditability.** Enterprises evaluating Despia can read the runtime that executes their apps rather than take its behaviour on trust. This is the main blocker we hear in enterprise reviews.
  - **Compliant deployments.** Under MIT, an organisation can vendor the kernel into its own internal build where compliance requires it, without a dependency on Despia infrastructure.
  - **A usable runtime on its own.** The kernel is functional without our packages. Writing your own WebView package, native UI package, and component implementations against the contract gives you a working runtime at no cost.

  This is not a wind-down of the commercial product. Despia's hosted platform, build pipeline, OTA updates, native packages, and support continue as they are, and open sourcing the kernel is intended to expand where Despia can be adopted, not reduce it. The goal is for Despia - hosted or self-hosted - to be the default runtime for AI-assisted development of production apps that stay maintainable and stay current through OTA updates.

  Nothing changes for existing apps. No dashboard configuration changes, rebuild steps, or integration code changes are required. Repository and license details will be published with the V4 release.
</Update>

<Update label="July 07, 2026" description="Sandbox Testing - repoint a build at a staging environment at runtime">
  ## Sandbox Testing

  Sandbox Testing lets a compiled app be repointed at a test environment at runtime, without rebuilding. Testers can redirect the running app to a staging host and start URL, run QA against the test backend, then restore the production app when they are done.

  **What ships today:**

  - **Point at a test environment.** The `sandbox://set` command overrides the runtime host and start URL, persists the override, and reloads the WebView into staging. Pass a `host`, a `start_url`, or both, and the missing value is derived from the other.
  - **Return to production.** The `sandbox://clear` command restores the production host and start URL from the snapshot captured at launch and reloads into the production app.
  - **Read the current environment.** `despia.isSandbox` is `true` whenever a test environment is active and `false` in production, so the page can branch on which backend it is talking to.
  - **Persists across launches.** An active override survives a cold launch. Every launch into a test environment shows a reminder alert, and each switch shows a native alert, so it is always clear which environment is live.
  - **Identical on both platforms.** The commands, the persisted behaviour, and `despia.isSandbox` work 1:1 on iOS and Android.

  See the [Sandbox Testing](/native-features/sandbox) documentation for the full parameter reference and QA flow.

  The feature is part of the native runtime, so it is available in builds created from today onward. No dashboard configuration or integration code is required to receive it, and the commands are callable directly from your loaded page.

<Update label="July 5, 2026" description="Audio - native player with lock-screen controls and feed pagination">
  ## Native audio player

  The native audio player is now. Hand the native side a fixed queue or a paginated feed and it owns playback end to end: background audio, lock-screen and Control Center controls, interruption handling, and route changes, all without your page touching an audio element.

  **What ships today:**

  - **Queue and feed playback.** The `audio://setqueue` scheme takes a fixed track list, and `audio://setfeed` points the player at a paginated server endpoint that it fetches ahead of time so the queue never runs dry.
  - **Full transport controls.** `audio://play`, `pause`, `next`, `prev`, `playat`, `seek`, `skipforward`, `skipback`, and `speed` drive playback from your own UI, and the lock-screen buttons fire the same commands.
  - **Live config without a restart.** The `audio://config` command toggles loop, playback speed, skip interval, and which lock-screen controls show, all while playback continues.
  - **Lock screen and background.** Every track renders a Now Playing card across the lock screen, Control Center, Dynamic Island, CarPlay, and watch. Playback keeps running when the app is backgrounded or the screen locks, pauses for calls and Siri, and resumes automatically.
  - **State through one callback.** All state changes arrive through a single `window.onAudioEvent` handler, including a 1 Hz progress tick, so your UI stays correct no matter who pressed the button.
  - **Server-side progress tracking.** The `audio://webhook` command POSTs playback milestones to your backend, including ones triggered from the lock screen while your web app is suspended.
  - **Reload survival.** Native playback outlives web view reloads and in-app navigation. Call `audio://sync` on page load to re-hydrate your UI to what is already playing.

  Full scheme, parameter, and event reference is in the [Audio documentation](/native-features/audio-player).

<Update label="May 10, 2026" description="Plugin bridge - window.despia switches to window.virtual.href after 15 years">
  ## window.virtual.href - 15 years later, a new plugin bridge

  After 15 years of routing every plugin call through `window.location.href` URL redirects, the bridge finally has a successor: `window.virtual.href`. This is a transparent internal architecture change on both iOS and Android, scoped to the `window.despia` and `despia()` paths. No code changes, no rebuilds, no NPM updates, no dashboard configuration - nothing on the developer side moves. The `window.despia` proxy now forwards to `window.virtual.href` instead of `window.location.href`, which removes the platform webview's URL character limit and eliminates the dropped-call risk caused by the navigation queue collapsing back-to-back navigations.

  **Direct `window.location.href` plugin calls are unaffected and stay fully supported.** Over 7,500 apps - including most projects built with Despia before 2023 - call `window.location.href = "myscheme://..."` directly rather than going through the `window.despia` abstraction. That path is now the legacy bridge, but legacy here only means "the older path" - it remains active, fully maintained, and will continue to receive new feature support and improvements over time. Nothing about it is deprecated, and no app on the direct path needs to migrate, now or later.

  For 15 years, the `window.location.href` redirect was the only way native code got triggered from the webview. It worked, but it inherited the platform webview's URL character cap - roughly 2KB on iOS WKWebView and a similar practical ceiling on Android WebView. Large payloads such as base64-encoded images, long AI prompts, or JSON blobs were silently truncated or rejected before native code ever saw them. Firing multiple plugin calls back-to-back was also unreliable, because the navigation queue on both WebKit and Android WebView could collapse them and silently drop the second call. `window.virtual.href` removes both constraints.

  **Why nothing needs to change in your code.** Every Despia NPM package and the `despia()` helper have always called `window.despia`, never `window.location.href` directly. `window.despia` is a proxy: it used to forward to `window.location.href`, and it now forwards to `window.virtual.href`. This migration was planned from day one. `window.despia` was built as a proxy specifically so this kind of switch could happen invisibly - and today it has. The `despia()` calls already in your code keep working unchanged on both iOS and Android.

  **What ships today for `window.despia` and `despia()` users:**

  - **No character limit.** Pass multi-megabyte payloads directly on iOS and Android. Full base64 images, long prompts, JSON dumps, and config blobs all go through intact.
  - **No dropped calls.** Fire as many plugin calls in a row as you want, in any order. Every call runs on both platforms.
  - **Free-form strings.** Spaces, special characters, and newlines pass through as-is with no manual encoding required.
  - **Same syntax as before.** `window.virtual.href = "myscheme://..."` uses the same scheme and parameter shape as the redirect path it replaces. The string is delivered straight to native code via a message channel instead of going through the URL redirect machinery.

  **Why the URL scheme syntax stays.** Despia plugin calls keep the `myscheme://method?param=value` shape on both bridges, and that is a deliberate choice rather than a legacy quirk. JSON-based bridges have their place, but URL schemes have real advantages worth keeping: one-line calls compose cleanly, they grep and search trivially across a codebase, and they read well to AI coding tools, which handle flat scannable text far better than nested object payloads. The single meaningful argument against the URL approach was always the 2KB cap. With `window.virtual.href`, that cap is gone - so the syntax keeps every advantage and loses its only real drawback.

  **Who this affects:** developers using the `despia()` NPM helper or assigning to `window.despia` directly. They get the upgrade automatically on their next deployment.

  **Who this does not affect:** developers calling `window.location.href = "myscheme://..."` directly. That bridge stays exactly as it was, with full support and continued investment in new features and improvements.

  No dashboard configuration changes, rebuild steps, code changes, or NPM package updates are required. Existing iOS and Android apps both inherit the appropriate behaviour automatically on their next deployment.

<Update label="March 30, 2026" description="Auth - Apple Sign In via Apple JS SDK">
  ## Apple Sign In

  Despia now supports Sign In with Apple using the Apple JS SDK across iOS, Android, and web, with platform-aware behaviour and full documentation.

  **What ships today:**

  - **iOS native - native Face ID sheet.** On iOS, the Apple JS SDK with `usePopup: true` opens the native Face ID / Apple ID sheet directly inside WKWebView. No `oauth://` bridge is needed on iOS. The `id_token` is returned to your JavaScript callback with no page redirect, which avoids the blank white screen that causes App Store rejection when using a redirect-based flow.
  - **Android native - oauth:// bridge.** On Android, the `oauth://` bridge opens Chrome Custom Tabs for the Apple OAuth flow. `public/native-callback.html` receives the `id_token` and `code` in the URL hash and fires the deeplink to close the tab. The `oauth/` prefix in the deeplink is required.
  - **Web - Apple JS SDK popup.** On web, the Apple JS SDK popup returns the `id_token` directly to your JavaScript callback. No redirect flow is used.
  - **Two response mode options for Android.** The `fragment` mode redirects the browser directly to `native-callback.html` with `#id_token` in the hash - no backend POST handler needed. The `form_post` mode sends `code`, `id_token`, `state`, and `user` (name and email JSON, first login only) to your backend, which validates and redirects to `native-callback.html` with a session token.
  - **Plain HTML callback file.** `public/native-callback.html` is recommended over a React component for the callback page. React Router can strip the `#id_token` hash fragment on route change, causing tokens to disappear. The plain HTML file bypasses React Router entirely and reads the hash directly from the browser. Chrome Custom Tabs hides the URL bar, so the `.html` extension is never visible to users.
  - **React, Vue, Vanilla JS, and HTML auth page examples.** All auth page examples include the `searchParams` dependency array fix to handle the already-mounted page problem, where the deeplink updates the URL without remounting the component and the token handler never re-runs.

  Apple Sign In requires a Services ID configured in the Apple Developer Console with your domain and return URL registered. The client secret JWT generated from your `.p8` private key expires after 6 months - set a reminder to regenerate it before expiry or Apple Sign In will silently stop working.

  Full documentation is available at [Apple Sign In](/native-features/oauth/apple)

  **Packages:**

  - [despia-native](https://www.npmjs.com/package/despia-native)

  A rebuild is required. No dashboard configuration changes are required beyond enabling the Apple JS SDK script tag and configuring your Apple Services ID credentials in your backend auth provider.

<Update label="March 22, 2026" description="Local Server - generally available in beta">
  ## Local server

  Despia now ships a local server for iOS and Android. Your web build downloads to the device on first launch and is served from an on-device HTTP server at `http://localhost`. From that point on, the app boots with zero network latency and works completely offline.

  **What ships today:**

  - **On-device HTTP server.** Assets are served from `http://localhost`, not `file://` or a custom scheme. BrowserRouter, Vue Router, and any routing library that expects a real HTTP origin work without modification.
  - **First-launch hydration.** On first open, Despia fetches your web build from your existing hosting (Netlify, Vercel, AWS, or anything else) and caches it on the device. No migration required.
  - **OTA updates.** On startup, Despia fetches `despia/local.json` and compares the `deployed_at` timestamp with the cached value. If it has changed, the new build downloads in the background and applies on next launch. No app store review needed for HTML, CSS, JavaScript, image, or font changes.
  - **`@despia/local` build plugin.** Available for Vite, Webpack, Rollup, Nuxt, SvelteKit, Astro, Remix, esbuild, and any build system via a `postbuild` CLI hook. The plugin scans your output directory after each build and generates `despia/local.json` automatically.
  - **`despia-version-guard`.** A companion package for gating web UI features behind a minimum native runtime version. Supports React, Vue, Angular, Svelte, and Vanilla JS.

  **Store compliance.** The local server downloads web content only (HTML, CSS, JS, images, fonts). No native code or executables are downloaded after submission. The approach follows patterns established by Expo and is compliant with Apple App Store Guideline 3.3.2 and the Google Play Malicious Behavior Policy.

  **This feature is in final beta.** To request access, email [offlinemode@despia.com](mailto:offlinemode@despia.com).

  **Documentation:** [Local Server Introduction](/local-server/introduction) and [Reference](/local-server/reference).

  **Packages:**

  - [`@despia/local`](https://www.npmjs.com/package/@despia/local) — build plugin
  - [`despia-native`](https://www.npmjs.com/package/despia-native) — native SDK and JavaScript bridge
